# Progress

## What works
- Launcher as default home; status bar, header, action bar, tab bar, dock, app grid/list (Frequent, Favorites, All, custom pages).
- Hide All/Frequent; default home tab by page ID; hidden apps; sorting and sort scope.
- Search (fuzzy, type-to-search from home, Alt/Shift symbols); search overlay; optional external search modes.
- Notifications: ticker (typing animation), hub (list, filters, Clear All), notification applets (per-app icons + counts) or fallback “N Notifications”.
- Header and action bar center tap actions (app/shortcut/hub); click highlights (ripple, configurable color/opacity, no focus ring).
- Icon packs (per-page, dock, applets); icon picker search; global/fallback icon shaping.
- Dock: pinned apps, intent shortcuts, swipe-up actions, reorder, custom color.
- Tab bar: highlight color and opacity; double-tap action (lock screen / hub).
- Settings: full UI; export/import; Restart Launcher intent.
- Widgets on supported pages; key shortcuts (accessibility) optional.

## What’s left / in progress
- **Ticker/count refresh:** Ticker and count sometimes don’t update after clearing notifications until launcher restart; ensure `onNotificationsChanged` and related refresh paths update all relevant UI.
- **Page visibility:** Frequent/All “hidden” state should be persistent (no random reappearance when opening menu or after actions).
- **Applet icons:** Display quality and custom icon handling for notification applets (pixelation/custom icons).
- **General reliability:** Reduce “need to restart” for settings/view changes; document and then address restart-heavy behavior.
- **Planned (from backlog):** Call/contact search; notification hub items selectable (and trackpad selection for hub).

## Current status
- Two search fixes shipped in v1.5.2: the empty-search Google fallback launches in its own task so it shows up in Recents (it was inheriting the launcher's home task, which Android keeps out of Recents), and app search matches package names via a new pre-computed `AppInfo.normalizedPackage`. Package-only matches rank after name matches. Both the repository search and `SearchOverlay`'s page-scoped `filterItems` path needed the package change — searching from All/Frequent never reaches `AppRepository.searchApps`.
- v1.5.3 follow-up: the fallback flags are now `NEW_TASK | CLEAR_TASK`. `RESET_TASK_IF_NEEDED` only brought an existing search task forward, so a second fallback search reused the stale task and dropped the new query. `CLEAR_TASK` finishes that task first, which still yields a normal Recents entry.
- v1.5.4: resolution / display-size changes no longer blank the app icons for 2–3 s; the process-wide `AppRepository` keeps the list, packs and icon cache across the recreate (see `activeContext.md`). On-device verification pending (cloud emulator could not boot).
- v1.5.5: typing in the built-in search is instant. Removed the 80 ms debounce; the matcher is about 40× cheaper (precomputed words, no per-call regex); built-ins and icons are cached per session; contact lookups are latest-only on one worker with a per-session phone index; results are diffed instead of fully rebound. See `systemPatterns.md` → "Search keystroke path". On-device verification pending.
- Dialer fix (unreleased): the dial row and Enter use `DialNumber.dialable(query)`, which accepts only digits, `*`, `#`, one leading `+` and the separators space, NBSP, `-`, `(`, `)`, `.`; any letter hides the row. Enter dials a dialable query before launching the first result or falling back to web search, except in command mode. Letter-to-keypad conversion (`convertToDialDigits`) still feeds app-label and contact digit matching only.
- Google suggestions (unreleased): when no result matches the query as text and the query is not dialable, `SearchOverlay` asks `util/WebSuggestions` (suggestqueries.google.com, `client=firefox`) for up to 6 suggestions. Requests fire at once unless one started within 60 ms. Results are latest-only: superseded HTTP requests are left to finish, which keeps the keep-alive socket, and only fill the cache. A 64-entry LRU cache with a 10-minute TTL answers repeats instantly. A cached shorter prefix is narrowed and shown while the request runs. Search open pre-warms the connection, throttled to once a minute. `adb shell setprop log.tag.WebSuggestions DEBUG` logs the timings. `WebSuggestionsLatencyBench` (`SUGGEST_BENCH=1`) measures live latency. Offline or malformed responses show nothing. Rows live in their own `suggestionsBox`, outside the results adapter; tapping one runs `openWebSearchWithQuery` (fresh task). It is off in command mode and @-contact mode. Pref `searchWebSuggestions` (default on) is read once per session. Added the `INTERNET` permission.
- Search label removal (#14) was reverted in 1.6.0 at the user's request: the "Extended / All Apps / Frequents" label is back.
- Swipe down for notifications (unreleased): `LauncherActivity.handleSwipeDown` runs first in `dispatchTouchEvent`, and the decision logic lives in the pure `util/SwipeDownGesture`. A swipe can start only with no overlay open, and only if no view under the finger `canScrollVertically(-1)` or is a `ResizableWidgetFrame` in resize mode. Direction locks once the finger leaves the slop: horizontal or upward motion is rejected, and so is a finger held still past the long-press timeout (the start of a drag). It triggers at 64dp with dy ≥ 2·|dx|, or on a fast flick at UP. Children then get CANCEL and the rest of the stream is swallowed. Expansion order: `NotificationShade.expand` (reflection on `StatusBarManager.expandNotificationsPanel`, `EXPAND_STATUS_BAR`), then accessibility `GLOBAL_ACTION_NOTIFICATIONS`, then the in-app hub. Pref `swipeDownNotifications` (default on), toggled in Settings → Behavior.
- Usage-based search ranking (unreleased): `util/SearchRanker` grades matches into tiers (exact label, label prefix, later-word prefix, other name match such as substring, prefix-per-word or keypad digits, package only). Within a tier it orders by frecency, then label. Frecency is the launch score with a 7-day half-life, `bump = decay + 1`, compared via the time-invariant `rankKey = log2(score) + at/HALF_LIFE`. `AppRepository.usageKeys` caches those keys (rebuilt on stats load, patched on launch), so a keystroke never touches the DB. Room v2 adds `frecency`/`frecencyAt` through `MIGRATION_1_2`, seeded from `launchCount`/`lastLaunched`. `recordLaunch` and `toggleFavorite` share `statsWriteMutex`. Pref `searchUsageRanking` (default on; off means tier then alphabetical). Settings → Search has "Reset usage data" with a confirm: it zeroes counts, times and frecency and keeps favourites.
- Settings overhaul (branch `cursor/settings-overhaul-b470`): the flat scroll is now a category home list with sub-screens of grouped cards; every row shows title + current-value summary. Same pref keys; `SettingsPrefCoverageTest` checks every pre-overhaul pref and entry point is still reachable. See `systemPatterns.md` → "Settings structure". On-device verification pending.
- Backup & restore (branch `cursor/backup-restore-b470`): one versioned zip (manifest.json with per-entry SHA-256, plus prefs/, db/, assets/). It dumps every shared_prefs file, every DB table, and every data-dir file a pref points at. A restore is validated in full before any write, staged, journaled with a snapshot, and rolled back on failure or on the next launch (`backup/`). Old settings JSON exports are migrated as schema 1. On-device verification pending.
- App version 1.6.0 (versionCode 23): integration of #11–#18 on `cursor/integration-v1.6.0`.
- Search scroll reset (no version bump, after 1.6.1): reopening search kept the results grid scrolled to where it was left. Root cause: the overlay is only hidden between sessions, and `resetSession()` cleared the query, results state and highlight but never the scroll position. A same-query reopen also hands DiffUtil an identical list, so nothing moves. `resetSession()` (called by `show`/`showFilter`) now scrolls the results RecyclerView to position 0 and the AI answer panel to the top; the highlight was already cleared there. `SearchScrollResetTest` covers this.
- versionCode 26 (1.6.1): on the device, hardware Enter with a row highlighted still ran the search-bar query. Root cause: with an IME attached, hardware keys go to the IME before the activity. The IME turned Enter into `InputConnection.performEditorAction(IME_ACTION_SEARCH)`, which reaches only the field's editor-action listener, and that listener always ran `performExtendedSearch`. Robolectric tests sent Enter through `Activity.dispatchKeyEvent`, so they never took that path. Fix: every Enter-like path goes through `LauncherActivity.submitSearch` (Alt+Enter asks AI, otherwise the highlighted row opens, otherwise the old behaviour):
  - the activity key path (`handleSearchKey`);
  - keys delivered straight to the field (`onSearchFieldKey`: Enter, numpad Enter, DPAD center);
  - the editor action (`onSearchEditorAction`, for any action id). Its key-up half is swallowed, and a late action after the search closed is a no-op;
  - an IME-committed newline (an InputFilter strips it and submits). A newline used to end up in the query.
  - Plain Enter delivered straight to the field also used to run the search twice (key-down, then the key-up editor action). `SearchEnterPathsTest` has 21 tests, one per path, with and without a highlight, plus Alt.
- versionCode 25: the trackpad highlight is a subtle neutral fill: white at about 12% alpha, or black at about 10% on a light overlay background, with 6dp corners. It replaces the accent fill plus 2dp accent outline, which was too loud on the device. A pixel test checks a neutral blend of that strength over black, white and blue wallpapers, and over a light overlay background.
- versionCode 24: search is navigable with the trackpad (DPAD and trackball). Up/down move an accent highlight through the dial row, Google suggestions, the result grid (left/right move within it and wrap) and the AI "Open AI settings" action. Up past the first row returns to the field. DPAD center or a trackpad click opens the highlighted row, and so does Enter when a row is highlighted; with no highlight, Enter and Alt+Enter are unchanged. Typing while a row is highlighted clears it and goes to the field without losing characters, even if focus had been moved elsewhere. Any change to the results clears the highlight. Root causes: DPAD focus search from the field left the overlay for the home pager behind it (then the tab bar), where type-to-search ignored keys because the overlay was visible. The overlay's rows were focusable (clickable), but focus search ranked the pager behind the overlay first. Result items also draw no focus highlight (`defaultFocusHighlightEnabled=false`, a pressed-only ripple). The first DPAD_DOWN could also just move the field's cursor to the end. The "Extended search" label isn't a target, since Enter already does the same. See systemPatterns → "Search trackpad navigation". On-device verification pending.
- versionCode 23: long-press Enter didn't work on the device keyboard and was removed. The in-search trigger is now Alt+Enter (`LauncherActivity.onSearchEnterKey`), behind pref `aiAltEnter` (default on, Settings → AI answers "Alt+Enter asks AI"). Alt counts if the event's meta state has `META_ALT_ON` or the system `META_ALT_LOCKED`, or if the field's `MetaKeyKeyListener` state on the text is sticky or locked (`AiSearchTrigger.altActive`). A sticky Alt is spent through `adjustMetaAfterKeypress`. The whole key press, including the UP after Alt is released, is consumed, so there is no Google fallback and no newline (the field is `maxLines=1`, not `singleLine`). Plain Enter is untouched. A long press on the action-bar search icon (`btnSearch`) triggers the same AI flow; it is always on, has no setting, and taps are unchanged. Robolectric's virtual keyboard can't produce sticky Alt (it uses chorded modifier behaviour), so the test drives `QwertyKeyListener` in its pressed state instead.
- versionCode 22: AI answers in search (package `ai/`). Triggers: Alt+Enter (see versionCode 23), the exported trampoline `.ai.AiSearchActivity` (action `com.meowgi.launcher710.action.AI_SEARCH`, Theme.NoDisplay, launcher task affinity), or a broadcast with that action. On trigger the Google suggestions clear and a spinner shows in the results area; the answer streams over SSE (`stream:true`) and renders as basic markdown (`AiMarkdown`) in a ScrollView. Typing, closing or reopening search cancels the request and disconnects the HTTP stream. Errors show inline with an "Open AI settings" link, which opens Settings on the AI screen. Settings → AI answers: enable, base URL, API key, fetch models (GET {base}/models), model picker with manual entry, system prompt, and Test. The API key is AES-GCM encrypted with an Android Keystore key in its own prefs file `ai_secrets`, which is excluded from the launcher backup (`BackupEngine.EXCLUDED_PREF_FILES`, on both capture and restore) and from Android backup (`res/xml/backup_rules.xml`, `data_extraction_rules.xml`). The other AI prefs (`ai*` in LauncherPrefs) are backed up normally. On-device verification pending.
- versionCode 21:
  - Faster suggestions (see above). With a +60 ms RTT, the first suggestion takes 75 ms instead of 415 ms, and each keystroke 75–80 ms instead of 280 ms.
  - Settings now runs in its own task (`taskAffinity` `<applicationId>.settings`, opened via `SettingsActivity.intent()` with NEW_TASK), so it stays in Recents. A restore asks the launcher to reload through `LauncherActivity.reloadRequested`.
- Device-test fixes in versionCode 20:
  - The dial row accepts numbers typed as QWERTY keypad letters (w e r s d f z x c = 1–9, a = `*`, q = `#`, o = `+`; `DialNumber.keypadChar`), because the device keyboard delivers number keys as letters without Alt.
  - Google suggestions are suppressed only by text matches, not by keypad-digit matches (`WebSuggestions.shouldRequest`).
  - The Extended label is back.
  - Settings pads itself for the system bars: it clears the theme's translucent status flag and applies insets on `settingsRoot`/`settingsToolbar`.
  - Robolectric tests (`SearchOverlayDecisionTest`, `SettingsInsetsTest`) drive the real overlay and activities.
- Fixed a flaky `WebSuggestionsRequestTest`. Its `request()` helper read the results after the main-thread task returned, so under load an instant fake fetch could be counted as "shown synchronously". It now snapshots inside the task. Widening the race with a sleep made the old helper fail 5 tests every run, and the fixed helper passes.

## Known issues
- **Fixed, pending device verification:** crash on restore (`Fragment no longer exists for key f#N`) and `lateinit pagerAdapter` crash; launcher being killed in the background from icon-bitmap churn and per-resume full re-index. See `activeContext.md` for the root cause and the changes.
- Ticker and count can stay visible or stale after clearing notifications until launcher restart.
- Hiding Frequent or All can appear inconsistent (initially still there, after menu gone, etc.); should be persistently hidden.
- Notification applet icons can look pixelated or worse with custom icons.
- Some features (e.g. grid/list switch) may require launcher restart to apply fully.
- Notification hub: individual items not selectable; trackpad selection only highlights hub, not items (to be addressed later).
- Cheaper onResume (unreleased): `LauncherActivity` rebuilds the page grids, the dock and the click highlights only when a settings write was observed (`uiDirty`, set by a SharedPreferences listener registered in onStart and forced on onStop) or when `AppRepository.refreshStats()` reports changed usage stats (it now returns a Boolean). Otherwise a resume only reloads the stats rows. Known gap: pinned shortcuts removed externally by their owner app are picked up on the next dirty resume rather than immediately.
